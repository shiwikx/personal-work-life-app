# 用 Codex 从 0 到 1 开发一个 Windows 本地工作生活管理 APP：完整流程与 AI 辅助开发实践

> 项目关键词：Node.js、SQLite、原生 JavaScript、PowerShell、Windows 便携版、AI 辅助开发、Codex、自动化测试  
> 项目成果：8 个业务模块、39 项自动化测试通过、离线运行、Windows 便携包约 89.6 MB

## 摘要

这篇文章记录我从需求梳理、技术选型、数据库设计、前后端开发、桌面提醒、备份恢复到测试和打包发布的完整过程。

这个项目中，AI 不是一个“装饰性关键词”，也不是产品里调用了大模型接口。**AI 的真实定位是研发助手**：我使用 Codex 辅助需求拆解、代码生成、故障定位、测试补充和文档整理，但每一个输出都要经过实际运行、自动化测试和人工复核。

整篇文章会重点说明两件事：

1. 一个本地工作生活管理 APP 应该如何从 0 做出来；
2. AI 在每个阶段究竟做了什么、我是怎么向它描述任务的、生成结果又是怎么验证的。

## 一、项目最终做成了什么

这个 APP 面向 Windows 单用户使用，解决计划、学习、毕设、开发、求职和工作事项分散的问题。

一共包含 8 个一级模块：

- 首页总览
- 今日计划
- 毕设论文
- 学习计划
- 开发计划
- 秋招每日计划
- 工作计划
- 数据与设置

除了业务模块，还实现了这些基础能力：

- 本地 SQLite 持久化，刷新页面或重启程序后数据仍然存在
- 重复事项、优先级、提醒、完成状态和进度记录
- 今日计划与各业务模块之间的数据联动
- 浏览器关闭后仍可运行的提醒服务
- Windows 系统托盘和桌面悬浮窗
- 手动/自动备份、校验恢复和数据目录切换
- CSV 与 Excel 2003 XML 格式导出
- 浅色、深色主题和透明玻璃视觉
- 不依赖云服务、不登录、不访问外部网络

所有服务只监听 `127.0.0.1`，页面资源全部在本地，断网后仍可使用。

最终验收阶段，39 项自动化测试全部通过，Windows 便携包内置 Node.js 运行时，解压后可以直接启动。

## 二、先说明：AI 在这个项目里怎么用

我没有把项目包装成“AI 自动写完了整个 APP”。真实流程是：

```text
需求确认
  ↓
人工确定边界和验收标准
  ↓
AI 辅助拆解任务和设计数据结构
  ↓
人工确认方案
  ↓
AI 生成小范围代码
  ↓
本地运行 / 执行测试
  ↓
把真实报错和测试结果反馈给 AI
  ↓
AI 做最小修复并补充回归测试
  ↓
人工检查代码、行为和边界
  ↓
Git 提交并进入下一阶段
```

核心原则是：**AI 可以生成代码，但不能替我做最终判断；必须以运行结果作为事实来源。**

### AI 使用分工表

| 开发阶段 | 提供给 AI 的上下文 | AI 主要输出 | 人工验证方式 |
| --- | --- | --- | --- |
| 需求分析 | 目标、用户、模块、不能改变的限制 | 任务拆分、验收项、遗漏风险 | 逐条核对 PRD |
| 架构设计 | 运行环境、离线要求、数据安全要求 | 技术方案、目录结构、模块边界 | 评估依赖和可维护性 |
| 数据库 | 实体关系、状态变化、查询场景 | 表结构、索引、事务流程 | 检查边界和一致性 |
| 后端开发 | 接口输入输出、错误处理规则 | API、校验逻辑、查询实现 | 运行集成测试 |
| 前端开发 | 页面目标、交互规则、现有样式 | 页面结构、交互逻辑、样式 | 页面实际操作和截图检查 |
| 故障排查 | 复现步骤、错误日志、相关代码 | 原因假设、最小修复方案 | 复现问题并跑回归测试 |
| 测试补充 | PRD 验收项、历史缺陷 | 边界用例、回归用例 | 实际执行测试 |
| 文档整理 | 代码、验收记录、使用流程 | 使用说明、问题清单、文章初稿 | 对照真实实现删改 |

> 重要：项目本身没有接入大模型 API，因此不要把它描述成 AI Agent 产品。它更准确的定义是“使用 AI 辅助开发完成的本地软件项目”。

## 三、第 0 步：先写需求，而不是先让 AI 写代码

一开始我没有直接说“帮我做一个工作生活 APP”。这种描述太宽泛，AI 很可能生成一个只有几个页面的 Demo，看起来能运行，但无法长期使用。

我先明确了 5 个必须满足的条件：

1. 数据只保存在本机，不登录、不联网、不使用云数据库。
2. 浏览器关闭后，提醒仍然要工作。
3. 计划类事项必须支持日期、重复、提醒、完成状态和进度。
4. 完成事项不能从模块中直接消失，要保留完成记录。
5. 备份、恢复和切换数据目录不能造成数据损坏。

然后逐项拆成模块、业务数据和验收标准。

例如“今日计划”不是简单地显示一个任务列表，而是要明确：

- 用户可以自己添加事项；
- 要自动汇总各业务模块当天的数据；
- 重复事项要按日期计算实例；
- 完成某一天，不应该关闭整个重复规则；
- 首页和所属模块的完成状态要同步；
- 完成后继续保留记录，但默认排在未完成事项之后。

### 我给 AI 的需求拆解提示词

```text
你是软件项目的需求分析师。
请根据下面的产品目标，输出：
1. 一级模块和每个模块的核心职责；
2. 每个模块必须具备的增删改查操作；
3. 跨模块共享的状态和字段；
4. 必须先确定的非功能要求；
5. 可以明确排除的范围。

约束：
- 单用户、Windows、本地运行；
- 不登录、不使用云服务；
- 数据必须本地持久化；
- 浏览器关闭后仍要提醒；
- 不要在需求阶段直接写代码。

产品目标：……
```

AI 给出的内容不能直接当作最终 PRD。我会重点检查三类问题：

- 是否把“提醒”误写成“打开页面时才检查”；
- 是否把重复事项提前生成成无限条数据；
- 是否加入了当前版本不需要的复杂功能。

这一阶段人工做决定，AI 只负责扩大思考范围。

## 四、第 1 步：技术选型与架构调整

### 1. 初始方案

最初的开发计划考虑过：

- Electron + TypeScript 作为桌面壳
- React + Vite 作为页面
- Fastify 提供本地 API
- SQLite 保存数据
- Drizzle 做 ORM
- Vitest 和 Playwright 做测试
- electron-builder 打包

这个方案本身没有问题，但对当前项目有一个现实限制：**开发环境无法稳定访问 npm 仓库**。

### 2. 最终采用的零第三方依赖方案

为了保证项目能继续开发和离线运行，我最终改成：

| 能力 | 实际实现 |
| --- | --- |
| 本地服务 | Node.js 内置 `node:http` |
| 数据库 | Node.js 内置 `node:sqlite` |
| 页面 | 原生 HTML、CSS、JavaScript |
| 桌面助手 | PowerShell WinForms / NotifyIcon |
| 自动化测试 | Node.js 内置 `node:test` |
| 页面验收 | Headless Chrome / Edge |
| 压缩包 | 项目内实现 ZIP 读写 |
| 发布方式 | 内置 Node.js 的 Windows 便携包 |

这个选择不是为了“显得简单”，而是为了降低运行环境不确定性。项目最终不需要安装第三方依赖，也不需要联网启动。

### 3. AI 在架构阶段怎么参与

我没有只问“推荐什么技术栈”，而是把约束一起交给 AI：

```text
请根据以下约束审查技术方案：
- Windows 单用户
- 可以断网运行
- 不依赖云服务
- 本地服务只监听 127.0.0.1
- 开发环境可能无法安装 npm 依赖
- 需要浏览器关闭后的提醒
- 需要 SQLite 备份与恢复
- 最终要生成便携包

请输出：
1. 哪些依赖可以去掉；
2. 哪些能力必须由当前运行环境自带的模块实现；
3. 可能出现的风险；
4. 不改变功能目标的最小可行架构。
```

AI 能给出方案，但最后的取舍必须由人完成。例如“使用原生 HTTP 服务”可以减少依赖，但路由、静态文件、错误处理和测试都要自己写，这部分工作量需要在计划里体现。

## 五、第 2 步：建立可运行的工程骨架

我先建立一个最小可运行系统，而不是一次生成全部模块。

目录大致如下：

```text
src/
  client/          页面、样式和交互
  core/            日期、调度、提醒、备份等核心逻辑
  server/          本地 HTTP 服务、API、进程入口
scripts/           启动、停止、桌面助手和打包脚本
tests/             单元、接口和端到端测试
docs/              用户说明、备份说明和验收记录
PRD.md             产品需求文档
DEVELOPMENT_PLAN.md 开发计划
```

启动本地开发版：

```powershell
node src/server/cli.mjs --open
```

或使用启动脚本：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/start-app.ps1
```

这一阶段必须满足：

- 本地服务可以启动；
- 页面可以通过 `127.0.0.1` 打开；
- `/api/health` 能返回健康状态；
- 数据库可以初始化；
- 刷新页面不会丢失数据；
- 断开网络不影响启动。

### AI 生成工程骨架时的约束

```text
请基于当前目录结构实现最小可运行骨架。
要求：
1. 不使用任何第三方 npm 依赖；
2. 服务只监听 127.0.0.1；
3. 提供健康检查接口；
4. 静态页面由本地服务提供；
5. 数据库路径可配置；
6. 先不要实现具体业务模块；
7. 完成后列出新增/修改文件，并说明如何启动和验证。
```

每次让 AI 只完成一个可验证的小目标，比一次要求它“完成整个系统”更可靠。

## 六、第 3 步：先设计数据底座

这个 APP 的难点不是页面多，而是不同模块都需要共享日期、重复、提醒、完成和进度逻辑。

最终没有为每个模块复制一套相同字段，而是抽象出通用实体模型。

核心表包括：

- `entities`：事项主体，记录模块、类型、标题、日期、状态、父级关系等；
- `occurrence_states`：某一天的具体实例状态，记录完成时间、提醒时间、稍后提醒时间；
- `settings`：应用设置；
- `memos`：快速备忘；
- `timer_state`：学习和开发计时状态；
- `backup_records`：备份历史。

设计时明确了几个约束：

1. 重复事项不预生成无限条记录，只按查询日期计算；
2. 完成某一天只影响该实例，不影响整个重复规则；
3. 父子任务通过 `parent_id` 关联，为自动进度提供依据；
4. 完成状态、提醒状态和手动进度不能互相覆盖；
5. 删除父项时使用外键级联清理子项；
6. 关键写入使用事务，避免只写成功一部分。

### AI 辅助数据库设计的提示词

```text
请根据以下业务规则设计 SQLite 表结构：
- 支持每天、每周、每月和自定义周期；
- 重复事项不能提前生成无限数据；
- 需要按日期查询当天实例；
- 需要保存完成、提醒、稍后提醒状态；
- 需要父任务和子任务；
- 需要同时支持自动进度和手动进度；
- 需要备份记录和设置；
- 要提供索引、外键和事务建议。

请先输出表结构、字段用途、唯一约束和查询场景，再写 SQL。
不要为了“以后可能需要”添加当前不使用的表。
```

数据库设计完成后，我会重点人工检查：

- 某个日期重复事项的唯一性如何保证；
- 删除父项后子项是否会留下孤儿数据；
- 恢复数据库时连接和事务是否安全；
- 计时器刷新后为什么还能恢复。

## 七、第 4 步：实现本地 HTTP 服务和 API

项目使用 Node.js 内置 `http` 模块提供本地服务，主要接口包括：

- `/api/entities`：通用事项 CRUD
- `/api/today`：今日计划汇总
- `/api/home`：首页摘要
- `/api/development/stats`：开发进度和时长统计
- `/api/autumn/summary`：秋招事项摘要
- `/api/work/reports`：日报和周报
- `/api/reminders/*`：提醒查询和补发
- `/api/backups/*`：备份与恢复
- `/api/exports/package`：完整数据包导出
- `/api/health`：健康检查

后端不仅负责读写数据库，还要处理：

- 输入参数校验；
- 重复事项实例计算；
- 完成与取消完成；
- 自动进度与手动进度合并；
- 事务提交和失败回滚；
- 本地静态资源返回；
- 服务重启后的状态恢复。

### AI 写接口时最容易出现的问题

如果只说“写一个任务接口”，AI 往往会遗漏异常路径。更有效的做法是把输入输出和错误行为一起写清楚：

```text
请实现 /api/entities 的新增、查询、修改、删除接口。
要求：
1. 校验必填字段、日期格式和数字范围；
2. 无效输入返回明确错误，不写入数据库；
3. 删除父项时，子项和实例状态按既定规则处理；
4. 所有涉及多表写入的操作使用事务；
5. 不引入第三方依赖；
6. 补充接口测试，覆盖正常流程、空参数和非法状态；
7. 完成后运行测试，并报告真实结果。
```

接口完成后必须实际调用验证，不能只相信 AI 说“已经完成”。

## 八、第 5 步：实现重复事项、完成状态和进度核心

这是整个项目最重要的共享逻辑。

### 1. 重复事项

查询某一天时，不是从数据库里取出无限个任务，而是根据事项的重复规则判断它是否发生在目标日期。

这样做的优点：

- 不会因为“每天重复”产生无限数据；
- 修改重复规则后，历史记录更容易保持一致；
- 某一天完成后可以单独保存实例状态；
- 今日计划和模块页面使用同一套判断逻辑。

### 2. 完成状态

- 非重复事项完成后，更新事项主体状态；
- 重复事项完成后，更新对应日期实例的 `occurrence_states`；
- 已完成事项在今日计划中保留显示，但使用弱化样式；
- 所属模块可以继续查看完成历史。

### 3. 进度计算

项目同时支持两种进度：

- 自动进度：根据子任务完成比例计算；
- 手动进度：用户直接填写百分比和进度说明。

最终进度采用明确的优先级：手动进度优先，其次自动进度，最后根据完成状态判断。两种数据分开保存，避免一边修改覆盖另一边。

### AI 辅助核心逻辑的方式

```text
请阅读现有 schedule、db、routes 模块，找出重复事项和完成状态处理中的边界问题。
重点检查：
1. 月末日期；
2. 每天、每周、每月和自定义周期的边界；
3. 完成某一天后，其他日期是否仍然存在；
4. 重复事项取消完成后是否能恢复；
5. 自动进度和手动进度是否互相覆盖。

不要直接重写全部代码。
先列出问题和测试用例，再给出最小修改方案。
每修复一个问题，都要添加回归测试。
```

这种“先分析、再测试、后修改”的顺序比直接让 AI 重写核心模块安全得多。

完成通用底座后，再逐个模块开发。

我没有让 AI 一次生成 8 个模块，而是每次处理一个模块或一个明确功能点。这样上下文更清楚，出现问题时也更容易定位。

## 十、第 7 步：页面开发与视觉迭代

前端使用原生 HTML、CSS 和 JavaScript，页面资源和图标全部本地提供。

视觉上参考了 macOS 天气 App 的透明玻璃效果：

- 彩色天空背景；
- 半透明玻璃卡片；
- 1px 边缘高光和柔和阴影；
- 浅色与深色主题；
- 本地保存主题选择；
- 不依赖在线字体、图标或 CDN。

桌面悬浮窗还支持：

- 始终置顶；
- 自由拖动；
- 收起；
- 四边和四角缩放；
- 尺寸切换；
- 系统托盘恢复。

### AI 做 UI 时的正确用法

“把页面做得高级一点”这种要求太模糊，AI 只能猜。实际使用时要把约束写清楚：

```text
请先阅读现有 styles.css 和 app.js，仅修改视觉和交互层，不改变业务数据结构。
要求：
1. 参考 macOS 天气 App 的透明玻璃质感；
2. 使用本地 CSS，不引入字体、图标和图片 CDN；
3. 浅色、深色主题都必须保证文字对比度；
4. 添加表单默认折叠，所有字段必须有可见标签；
5. 已完成事项继续显示，但排在未完成事项之后；
6. 先说明会修改哪些文件，再实施；
7. 修改后检查页面是否出现横向滚动、遮挡和错位。
```

视觉迭代也不能只看 AI 描述。我会打开页面、截取实际效果，再把问题反馈给 AI，例如“悬浮窗右侧关闭按钮被裁切”或“完成事项刷新后消失”。AI 根据真实现象修改，而不是根据想象修改。

## 十一、第 8 步：提醒与 Windows 桌面助手

浏览器关闭后的提醒是这个项目的关键难点。

### 1. 运行结构

```text
Windows 启动脚本
  → 启动 Node.js 本地服务
  → 健康检查
  → 打开浏览器
  → 启动 PowerShell 桌面助手

Node.js 后台服务
  → 每 15 秒检查到期提醒
  → 处理免打扰、稍后提醒和已提醒状态

PowerShell 桌面助手
  → 系统托盘
  → 今日未完成悬浮窗
  → 提醒弹窗和操作按钮
```

### 2. 关键处理

- 提醒由后台服务调度，不依赖浏览器页面；
- 每个实例使用唯一键避免重复提醒；
- 电脑关机期间错过的提醒在启动后补发；
- 免打扰时间段内不弹窗；
- 支持稍后 10 分钟；
- 支持完成、打开详情和关闭；
- 单实例锁避免重复启动造成重复提醒。

### 3. AI 如何协助排障

提醒问题很难只靠看代码定位，必须提供日志、时间点和复现步骤：

```text
现象：关闭浏览器后，到点提醒没有出现。
复现步骤：
1. 创建一条 2 分钟后的事项；
2. 关闭浏览器；
3. 等待 3 分钟；
4. 托盘仍在，但没有提醒弹窗。

预期：后台触发提醒。
实际：无提醒。

请检查：
1. 服务是否仍在运行；
2. 提醒时间计算是否正确；
3. occurrence_states 是否被提前标记为已提醒；
4. 禁止打扰时段是否误判；
5. PowerShell 通知调用是否失败。

请先基于日志和代码指出最可能原因，不要直接改完整模块。
```

桌面托盘、通知权限、多显示器和开机自启动仍需要在真实 Windows 环境中人工检查，自动化测试只能覆盖代码路径和配置逻辑。

## 十二、第 9 步：备份、恢复和导出

本地应用最大的风险不是页面报错，而是数据丢失。因此备份恢复必须按“失败也不能破坏原数据”的原则实现。

### 备份包内容

```text
backup-时间-随机标识.zip
├── manifest.json   格式版本、备份时间、备份类型
├── settings.json   应用设置
└── app.sqlite      WAL checkpoint 后的数据库快照
```

### 恢复流程

```text
选择备份
  → 校验 ZIP 结构
  → 校验 manifest 和数据库格式
  → 自动创建恢复前安全备份
  → 在安全条件下替换数据库
  → 校验恢复结果
  → 成功则记录恢复时间
  → 失败则保留原数据库并记录错误
```

自动备份每天首次启动执行一次，支持保留数量限制。导出支持 UTF-8 BOM CSV 和 Excel 2003 XML（`.xls`），适合直接使用 Excel 打开。

### AI 在数据安全流程中的提示词

```text
请审查当前备份和恢复逻辑。
必须满足：
1. 恢复前自动生成安全备份；
2. 备份缺失 manifest 或数据库时拒绝恢复；
3. 恢复失败不能破坏当前可用数据库；
4. 切换数据目录失败时不能静默写入新目录；
5. 所有异常都要有明确错误信息；
6. 补充失败路径测试。

请输出风险点、修改方案和测试结果。不要只测试成功路径。
```

AI 很容易写出“成功路径可用”的代码，但备份恢复真正需要验证的是失败路径。

## 十三、第 10 步：自动化测试与验收

最终验收阶段记录了 39 项自动化测试，覆盖接口、业务逻辑和页面。

测试包括：

- 数据库重开和服务重启后的持久化；
- 8 个一级页面渲染和导航；
- 重复事项、完成与取消完成；
- 自动进度和手动进度；
- 学习、开发计时恢复；
- 提醒提前量、补发、免打扰和稍后提醒；
- 备份、恢复和导出；
- 数据目录切换；
- 单实例锁；
- 损坏备份和异常路径；
- Headless Chrome/Edge 页面检查。

常用命令：

```powershell
pnpm test
pnpm test:e2e
```

或者直接执行：

```powershell
node --test tests/stage5-modules.test.mjs
node --test tests/e2e/acceptance.test.mjs
```

### 让 AI 补测试的正确流程

不要只说“帮我提高测试覆盖率”。更有效的方式是给出验收项和历史缺陷：

```text
请根据以下功能规则补充自动化测试：
1. 重复事项今天完成后，明天仍然应该出现；
2. 完成事项继续保留在模块历史中；
3. 刷新页面后计时状态不丢失；
4. 恢复损坏 ZIP 时原数据库仍可读取；
5. 关闭浏览器后提醒仍由后台处理。

要求：
- 先列出测试用例和预期结果；
- 再编写测试；
- 每个用例只验证一个核心行为；
- 不修改业务代码来“让测试通过”；
- 最后实际运行测试，并粘贴真实结果。
```

我会要求 AI 报告真实测试输出。测试命令失败时，把完整报错反馈回去，并要求它先定位原因，再做最小修复。

## 十四、第 11 步：打包 Windows 便携版

项目最终打包成 Windows 便携包，而不是要求用户先安装 Node.js。

打包流程：

```text
复制源码、脚本和文档
  → 复制 Node.js 运行时
  → 生成启动、停止、打开悬浮窗脚本
  → 写入发布清单
  → 打包 ZIP
  → 解压到全新目录
  → 启动并通过健康检查
```

生成命令：

```powershell
node scripts/package-windows.mjs
```

发布包包含：

- `runtime/node.exe`
- 主程序和静态页面
- 启动、停止脚本
- 用户说明
- 备份恢复说明
- 发布清单

最终包体约 89.6 MB，主要体积来自内置 Node.js 运行时。发布前必须在一个全新目录解压并启动验证，不能只在开发目录里测试。

## 十五、第 12 步：真实迭代与 AI 使用经验

Git 提交记录反映了这个项目并不是“一次生成就结束”，而是持续迭代：

- 优化页面和悬浮窗视觉；
- 明确五级优先级；
- 增加模块已完成任务存档；
- 优化今日事项添加表单；
- 在悬浮窗显示学习计时；
- 增加首页全局进度条；
- 修复秋招下一场笔试面试更新；
- 修复悬浮窗缩放和关闭按钮；
- 保留今日计划完成记录；
- 多次调整透明玻璃和深色主题。

这些迭代让我总结出几条 AI 辅助开发经验：

### 1. 一次只让 AI 做一个小目标

错误方式：

```text
帮我把整个 APP 做完。
```

更可靠的方式：

```text
先只完成今日计划的查询接口和对应测试，不修改其他模块。
```

### 2. 上下文比“提示词技巧”更重要

给 AI 提供：

- 当前目标；
- 相关文件和目录；
- 已有的数据结构；
- 不可改变的规则；
- 预期行为；
- 实际报错；
- 验证命令。

### 3. 让 AI 先分析，再修改

尤其涉及数据库、完成状态和备份恢复时，直接让 AI 重写整个文件很危险。先让它列出原因、影响范围和测试用例，再修改最小代码。

### 4. 用真实结果反馈，而不是继续猜

不要把“我觉得还是不行”发给 AI。应该提供：

- 哪个命令失败；
- 完整报错；
- 复现步骤；
- 预期结果；
- 实际结果；
- 是否只在某个页面或某个时间点出现。

### 5. 人工负责边界和取舍

AI 可以快速生成 CRUD，但以下内容必须由人确认：

- 是否允许访问外部网络；
- 数据目录在哪里；
- 备份失败时如何回滚；
- 重复事项的完成语义；
- 哪些功能属于当前版本；
- 是否为了赶进度牺牲数据安全。

## 十六、可直接复用的 AI 研发提示词

### 1. 需求拆解

```text
你是需求分析师。请把下面的目标拆成可交付模块、用户操作、数据对象和验收标准。
禁止直接写代码。
标出跨模块共享的状态、可能的边界问题和当前版本应当排除的功能。
```

### 2. 局部实现

```text
请先阅读相关代码和测试，只实现下面这个功能，不重构无关模块。
实现要求：……
禁止事项：……
验证命令：……
完成后请列出修改文件、关键设计选择和真实测试结果。
```

### 3. 故障排查

```text
请根据以下复现步骤、错误日志和实际行为定位问题。
先给出至少两个可能原因，并说明如何验证，不要直接重写整个模块。
确认原因后做最小修复，并补充回归测试。
```

### 4. UI 调整

```text
请基于现有页面修改这个交互，不改变业务接口。
必须满足：……
需要保持：……
请在修改后检查布局、文字对比度、空状态和已完成状态。
```

### 5. 代码审查

```text
请从数据一致性、异常处理、边界条件、离线运行和测试缺口五个角度审查这段代码。
按严重程度列出问题，不要为了提出建议而重写代码。
```

## 十七、从开始到结束的完整流程清单

如果你也想做一个类似项目，可以按这个顺序执行：

1. 明确用户、使用场景和不做什么；
2. 把需求拆成模块和验收项；
3. 先确定数据保存位置和失败处理；
4. 选择最少依赖、能离线运行的技术方案；
5. 建立可启动的工程骨架；
6. 设计数据库和唯一约束；
7. 实现通用日期、重复、提醒和完成逻辑；
8. 打通首页和今日计划一条完整业务闭环；
9. 按模块逐个实现业务功能；
10. 在真实页面中检查交互，而不是只看生成代码；
11. 完成后台提醒、托盘和悬浮窗；
12. 实现备份、恢复和数据目录切换；
13. 为成功路径和失败路径补充测试；
14. 在全新目录中打包并验证启动；
15. 记录已知限制并准备用户说明。

AI 可以在第 2、3、5、6、7、9、12、13、15 步提供明显帮助，但不能替代第 1、4、10、14 步的人工判断和真实验证。

## 十八、项目结果与不足

### 已实现结果

- 8 个业务模块可运行；
- 数据保存在本地 SQLite；
- 支持重复计划、提醒、完成历史和进度；
- 浏览器关闭后后台仍可提醒；
- 支持系统托盘和桌面悬浮窗；
- 支持备份、恢复、导出和数据目录切换；
- 不依赖 CDN、云服务或在线账号；
- Windows 便携版内置 Node.js 运行时；
- 最终验收阶段 39 项自动化测试通过。

### 当前限制

- Windows 通知权限和开机自启动受系统策略影响；
- 悬浮窗在多显示器环境下的手感仍需人工检查；
- 某些安全软件可能首次拦截 PowerShell 脚本；
- `.xls` 导出使用 Excel 2003 XML 格式，并不是二进制 XLSX；
- 自动化测试通过不代表所有真实 Windows 生命周期场景都已完全覆盖。

## 十九、总结

这个项目让我对 AI 辅助开发有了更实际的理解。

AI 最有价值的地方不是“替我写几行代码”，而是帮助我快速完成这些工作：

- 把模糊需求拆成可验证任务；
- 生成可运行的初版实现；
- 根据真实报错缩小问题范围；
- 补充容易遗漏的边界测试；
- 整理用户说明和验收记录。

但项目能不能交付，最终取决于人是否做了这些事：

- 明确边界；
- 检查数据结构；
- 运行代码；
- 执行测试；
- 验证失败路径；
- 在真实 Windows 环境中确认行为。

**AI 提高的是迭代速度，不能替代工程判断。**

如果这篇文章对你有帮助，后续我也可以继续分享这个项目中“重复事项状态设计”“Windows 后台提醒”“SQLite 备份恢复”和“零依赖便携打包”的实现细节。
